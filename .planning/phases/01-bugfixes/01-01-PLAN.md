<objective>
Make the page-group transition state machine impossible to strand. Today `TransitionPageAsync` sets
`m_IsTransitionPage = true` on two pages and only clears it on the straight-line success path
(`Runtime/UIPage.cs:291-292` set, `Runtime/UIPage.cs:371-372` clear). Any cancellation, destroyed
page, or throwing consumer callback between those two points leaves both flags stuck at `true`
forever, and the group can never transition again. There is also no mutual exclusion, so two
overlapping calls that resolve different `_current` pages both proceed and fight over the same
group's state.

**Phase goal (verbatim from ROADMAP.md Phase 1):** Users of the package no longer hit the three known
reliability failures - transitions don't desync, stale editor state doesn't leak across play
sessions, and destroyed components don't crash the page.

This plan owns the first of those three: BUG-01.

Purpose: Roadmap success criterion 1 - "Rapidly calling `TransitionPageAsync()` twice on the same page
group no longer leaves `m_IsTransitionPage` desynced - the page group remains transitionable
immediately after, with no stuck/unresponsive state."
Output: A `Runtime/UIPage.cs` whose transition state machine always releases the state it acquires,
and admits exactly one transition per group at a time.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer game code -> `UIPage` public static API | Call ordering, timing, and re-entrancy are entirely attacker/caller controlled. The package cannot assume calls are well-spaced or well-formed. |
| consumer `IPageShow*` / `IPageHide*` handlers -> transition state machine | Third-party code executes *inside* the state machine's critical section and may throw, block, or re-enter. |
| DOTween tween + `CancellationToken` -> transition state machine | The awaited tween is the throw site that can abort the critical section at an arbitrary point. |
